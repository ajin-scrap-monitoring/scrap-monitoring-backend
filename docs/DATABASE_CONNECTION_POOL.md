# 비동기 DB 연결 재사용과 동시 조회

라우터는 비동기 함수이며 PostgreSQL은 SQLAlchemy AsyncSession과 asyncpg로 접근한다.
요청마다 별도 세션을 사용하고 엔진·연결 풀을 같은 앱 프로세스에서 공유한다. 미디어 HTTP와
SSE 대기 동안 인증용 읽기 트랜잭션을 유지하지 않는 기존 규칙도 그대로 따른다.

## 연결 개수

PostgreSQL 엔진은 연결을 최대 10개까지 풀에 유지하고 초과 연결은 최대 5개까지 연다.
프로세스당 최대 15개로, 이전 기본값인 재사용5+초과10의 최대 개수와 같다.
SQLite의 연결 옵션과 풀은 변경하지 않는다.

10개를 시작할 때 모두 미리 만드는 방식은 아니다. 필요할 때 연결하며 사용 후에는 풀에
돌려준다. 가벼운 조회가 8개씩 반복될 때 초과 연결 생성·인증·종료 비용이 반복되는 것을
줄인다. 첫 요청 묶음이나 서버 재시작·끊어진 연결의 재접속 비용은 여전히 발생할 수 있다.
기존 `pool_pre_ping=True`와 풀 대기·세션 commit/rollback·종료 시 dispose를 유지한다.

## 동시 처리의 의미와 범위

DB 응답이나 카메라 HTTP를 기다리는 동안 다른 요청은 진행할 수 있다. 동시에 도착한
요청을 순서대로 끝까지 처리하도록 강제하지 않는다. 다만 Python 계산·JSON 처리·DB 서버
부하·네트워크·연결 생성은 대기 시간을 만들 수 있어, 동시 조회가 항상 단독 조회와 같은
시간에 끝난다고 보장하지 않는다. 연결 15개가 모두 사용 중이면 다음 요청은 반환을 기다린다.

Uvicorn worker를 늘리는 변경은 포함하지 않는다. 여러 앱 프로세스라면 최대 연결 개수도
프로세스 수에 비례하며, DB의 전체 접속 예산에는 백업·관리 작업 등 다른 접속도 포함한다.
현재 미디어·경보 작업자와 고정 페이지 저장소의 단일 worker 전제를 유지한다. PostgreSQL의
최대 접속 수·사용자·권한·스키마와 앱 운영 환경 변수는 이 변경에서 수정하지 않는다.

실제 PostgreSQL 회귀 검증은 앱 엔진을 통해 8개 읽기 연결 묶음을 반복해 연결 재생성이
없는지 확인하고, 15개가 사용 중일 때 16번째가 대기하다 반환된 연결을 사용하는지 확인한다.
이 검증은 특정 응답 시간이나 현장 부하 전체를 보장하는 성능 기준을 대신하지 않는다.
