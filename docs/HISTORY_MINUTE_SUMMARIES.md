# 적재율 이력의 작은 분 요약

긴 기간의 PostgreSQL 이력 조회가 매번 모든 초별 근거 JSON을 가져오지 않도록,
`edge_v2_minutes.history_summary`에 완전한 분의 집계 결과를 함께 저장한다.
기존 `/api/v2/monitoring/load-history`의 요청·응답·단위·시간 제한은 유지한다.
화면에서 새 API를 연결하거나 평균을 다시 계산할 필요는 없다.

## 원본과 요약의 관계

`0004_minute_history_summary`는 nullable JSON 열 하나를 추가한다. 기존 행의
`payload`, `generated_at`, `created_at`, 표본·관측 ID와 시각은 변경하지 않는다.
테이블·인덱스를 추가하거나 과거 migration을 수정하지 않는다.

새 분 관측은 원문과 요약을 같은 트랜잭션에 저장한다. 요약은 유효·무효 개수,
합계·최솟값·최댓값, 제한된 출처·방법 목록, 마지막 표본의 실제 근거를 담는다.
같은 초의 표본 교체나 늦은 도착도 기존 분 집계 정책으로 다시 계산한다.

PostgreSQL 조회는 최대 128행씩 작은 요약을 읽고 출력 구간별로 합친다. 다음 경우에는
해당 분의 원문을 읽어 기존 알고리즘을 사용한다. 원문을 한 번에 가져오는 양도 128행 이하다.
버퍼에 이미 도착한 행도 묶음 사이에 실행을 양보하므로 다른 요청과 취소가 진행될 수 있다.
각 행의 UTC 시각은 한 번 정규화하고, 출력 구간의 누적 객체는 처음 필요할 때만 만든다.
이는 반복 처리 비용을 줄이며 요약 검증이나 원문 대체 조회 조건을 생략하지 않는다.
이는 단일 worker에서 긴 계산이 연속되는 시간을 제한하며, 동시 요청의 동일 응답 시간을
보장하거나 CPU 계산을 여러 프로세스로 병렬화한다는 의미는 아니다.

- 아직 요약이 없는 기존 행.
- 조회 시작·끝이 분 중간에 걸리는 최대 두 분.
- 요약 버전·형식 또는 행의 생성 시각이 맞지 않는 경우.
- 해당 분 바깥의 표본 등으로 요약을 사용할 수 없는 경우.

0%는 유효한 값으로 유지하고, 마지막 표본이 무효면 이전 정상값으로 대체하지 않는다.
입력 출처나 계산 방법이 섞였으면 `MIXED`와 기존 사유를 유지한다. 원래 세부 근거가 없으면
시각·관측 ID를 추정하지 않는다. 분의 마지막으로 도착한 표본과 시간상 가장 나중의 표본도
구분한다. SQLite 조회는 기존 SQL 집계 경로를 유지한다.

## 기존 자료의 요약 보완

스키마 변경과 보완 작업은 구분한다. migration 자체는 원문을 읽어 일괄 계산하지 않으며,
조회 API도 보완 데이터를 쓰지 않는다. 요약이 없는 행은 원문 조회로 계속 사용할 수 있다.
과거 자료의 조회 비용까지 줄이려면 새 쓰기 작업자가 동작한 뒤 아래 관리 명령을 실행한다.

백업·실제 대상 DB·관리 계정을 확인하고 [DB 마이그레이션](DB_MIGRATIONS.md) 절차로
구조를 먼저 적용한다. 구조 변경은 기존 관리 계정으로 실행하고, 요약 보완에는 해당
테이블의 SELECT·UPDATE 권한이 있는 기존 앱 계정을 사용할 수 있다. 실제 DB URL이나
비밀번호를 명령행 인자에 넣지 않는다.

```bash
# 현재 스키마 확인 및 남은 행 수 조회. 관측이나 요약을 수정하지 않는다.
uv run python -m src.app.cli.db check
uv run python -m src.app.cli.history_summaries status

# 기본은 128행 한 묶음만 처리한다. 아래는 최대 1,000묶음까지 보완하는 예다.
uv run python -m src.app.cli.history_summaries backfill \
  --batch-size 128 --max-batches 1000 --pause-seconds 0.1
```

런타임 이미지에서는 `uv run python` 대신 이미지 안의 Python을 사용한다.
운영에서는 검증된 배포 환경과 DB 네트워크를 쓰는 관리 컨테이너 하나에서 실행하고
CPU·메모리 제한을 유지한다. 다른 서비스·원본 영상·보관 정책은 변경하지 않는다.

한 묶음은 1~512행이며 매번 commit한다. 기본 묶음 사이 대기는 0.1초다.
진행 위치는 기본키로 이동하며, PostgreSQL에서는 잠긴 행을 기다리지 않고 건너뛴다.
잠금 대기 제한 1초와 SQL 제한 5초는 현재 보완 트랜잭션에만 적용한다.
원래 측정 필드를 UPDATE하지 않고 요약 열만 저장한다.

진행 로그는 처리 묶음·행 수만 제공하며, 마지막 JSON의 `remaining=0`, `complete=true`로
완료를 확인한다. 최대 묶음 수에 도달하거나 잠긴 행이 남으면 같은 명령을 다시 실행한다.
프로세스가 중단되어도 완료한 묶음은 남고, 다시 실행하면 아직 비어 있는 요약만 채운다.
기존 값을 덮어쓰거나 자료를 삭제하지 않는다. 정상 배치를 벗어난 분은 사용 불가 표시를
저장하고 계속 원문으로 조회하므로, 요약 행이 채워졌다고 모든 분이 최적화된 것은 아니다.

## 배포·복구와 성능 검증

기존 스키마에 새 이미지를 바로 기동하지 않는다. 검증한 백업과 구조 변경·호환 이미지
계획을 먼저 준비한다. schema 0004에서 이전 schema 0003 전용 이미지로 단순 복귀할 수 없다.
비상 복구 이미지는 0004 구조를 인식해야 하고, 분 원문을 쓰는 경우 같은 트랜잭션에서
요약을 다시 계산하거나 SQL NULL로 무효화해야 한다. DB downgrade로 원문을 삭제하지 않는다.
무효화할 때는 처음 읽은 요약이 이미 NULL이었더라도 원문 UPDATE에 NULL을 명시해야 한다.
사이에서 보완 작업이 요약을 저장했을 가능성이 있으므로 ORM의 변경 감지 생략에 의존하지 않는다.

성능 비교는 합성 자료로 기존 원문 경로와 새 요약 경로의 응답 전체를 비교한다.
90일 분 자료의 구간 수·집계값·복합 기본키 범위와 초별 근거가 많은 7일 자료를 함께 검증한다.
일부 분, 구형 행, 결측, 출처 변경, 재전송·같은 초 교체·늦은 도착과 동시 쓰기 잠금도 확인한다.

요약은 원문 전송·JSON 해석 비용을 줄이지만 항상 같은 응답 시간을 보장하지 않는다.
실제 보관량·캐시·동시 부하와 아직 보완하지 않은 행의 비율에 따라 시간이 달라진다.
기존 20초 처리 상한과 `503 HISTORY_QUERY_TIMEOUT`을 유지하며, 실패를 빈 그래프나 0%로
바꾸지 않는다. 로컬 합성 성능을 실제 서버의 7일·30일·90일 응답 시간으로 표시하지 않는다.
