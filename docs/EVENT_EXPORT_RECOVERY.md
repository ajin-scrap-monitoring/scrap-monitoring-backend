# 이벤트 구간 다운로드의 기존 작업 복구

같은 계정으로 다른 브라우저에 로그인해도 기존 구간 다운로드를 찾을 수 있다.
사용자가 명시적으로 새 요청을 보낼 때 처리 중이거나 준비된 파일을 재사용한다.
조회와 재생은 파일 생성·실패 재시도를 자동 실행하지 않는다.

## 기존 작업 조회

`GET /api/v2/recordings/events/{event_id}/exports?before_seconds=30&after_seconds=30`

로그인 필요, 조회 사용자·관리자 모두 허용, CSRF 불필요, 응답은no-store다.
이벤트 존재와 범위를 확인한 뒤 해당 계정·이벤트·문맥·현재 미디어 출처의 최근
작업을 반환한다. 응답 모델은 기존 `EventExportResponse`이며 없으면200과JSON null이다.
없는 이벤트는404이며 잘못된 문맥은422다. 다른 계정의 작업은 반환하지 않는다.

접수된 clip이 있으면 기존 미디어 상세 GET으로 상태를 갱신할 수 있다.
접수 응답을 잃어 clipId가 없는 pending 작업은 저장된 상태만 반환한다.
이 GET은 미디어 POST를 하지 않으며 새 작업·요청 별칭을 만들지 않는다.
원천 조회 실패는 기존 안전한 오류로 전달하고 상태를 정상으로 추정하지 않는다.

브라우저는 이벤트를 선택할 때 이 API로 복구하고, 작업이 있으면 응답의
`statusPath`를 사용한다. failed는 사용자 명시 재시도, deleted/expired는 사용자
명시 새 요청으로 처리한다. ready라도 `downloadPath`가 없으면 다운로드하지 않는다.
브라우저가 이전 UUID를 기억하지 않아도 이 조회로 찾을 수 있다.

## POST 재사용과 요청 번호

기존 `POST /api/v2/recordings/events/{event_id}/exports`와 요청 본문을 유지한다.
로그인·CSRF가 필요하다. 동일 UUID의 기존 계정·이벤트·문맥 결합은 변경하지 않는다.

새 UUID가 오면 같은 계정·이벤트·beforeSeconds/afterSeconds·미디어 출처와
확정된 실제 구간이 일치하는 기존 작업을 찾는다. pending/collecting/processing 또는
유효한 ready 파일이면200으로 그 작업을 반환한다. 준비된 파일은 원천 상세를 확인해
삭제·만료 파일을 재사용하지 않는다. 조회 실패 시 새 파일 생성으로 우회하지 않는다.
응답 유실로 clipId가 없는 pending 작업도 재사용하며 기존 작업자가 원래 키로 복구한다.

응답의 `requestId`와 `statusPath`는 **원래 작업의 값**이다. 새로 보낸 UUID와 다를 수
있으므로 이후 조회와 명시 재시도에는 응답 값을 사용한다. 새 UUID도 DB의 별칭으로
원래 작업에 영구 연결한다. 별칭 UUID로 기존 상태 조회를 할 수도 있지만 응답은 원래
작업의 ID를 사용한다. 해당 파일이 나중에 만료·삭제되어도 같은 별칭 재전송을 다른
파일로 바꾸지 않는다. 다른 이벤트·문맥에 재사용하면409다.

기존 작업이 failed/blocked/deleted/expired이거나 ready 파일의 유효 기간이 지났으면
새 UUID 요청은 새 작업을 만들 수 있다. 기존 UUID의 실패 재시도는 기존처럼
`retryFailed=true`가 필요하며 새 UUID의 retryFailed=true는404다.
다른 계정·문맥·출처·실제 구간에는 파일을 재사용하지 않는다.

미디어 GET은 정보를 갱신할 수 있지만 처리 중/ready 재사용은 새로운 미디어 POST를
하지 않는다. 기존 레코드에 별칭이 없어도 조회·재사용하며 일괄 backfill은 필요 없다.
별칭은 일반 이벤트 목록에 추가되지 않으며 별도 다운로드 파일도 아니다.

## DB 적용과 실행 기준

이 기능은 Alembic `0003_event_export_aliases`가 필요하다. 기존 스키마의 업무 데이터를
변경하지 않고 `event_export_aliases` 테이블과 job 참조 인덱스를 추가한다.
계정과 요청 UUID의 복합 기본 키로 원래 job과의 결합을 보존한다.

기존 DB는 백업·적용 시점·호환성을 확인한 뒤 관리 환경에서
`uv run python -m src.app.cli.db upgrade`를 실행한다. 런타임 이미지에서는
`python -m src.app.cli.db upgrade`를 사용한다. 앱은 시작 시 현재 스키마를 요구하므로
기존0002 DB에 새 이미지만 교체해서 적용하지 않는다. 기존0002만 아는 이전 앱으로의
복귀도 새 스키마 호환성을 먼저 확인해야 한다. 자동 downgrade와 업무 데이터 삭제는 하지 않는다.

새 요청·재사용·미디어 작업자는 기존 프로세스의 lock으로 직렬화한다.
현재 배포 기준은 단일 Uvicorn worker다. 여러 worker/서버 간 분산 선점과 중복 방지까지
보장하는 기능은 아니며 확장 전에 DB 차원의 작업 선점 설계가 필요하다.

새 작업의 구간·부분 영상·오류·파일 다운로드 규칙은
[이벤트 구간 MP4 다운로드](EVENT_RANGE_EXPORTS.md)를 따른다.
