# 사용자별 알림 읽음 상태

기존 알림함 API 경로와 응답 필드를 유지하면서, 읽음 여부와 미확인 개수를 로그인 계정별로 계산한다. 관리자와 조회 사용자 모두 자신의 읽음 상태를 관리할 수 있다. 알림 내용 자체는 기존처럼 공통 경보 목록이며, 연락처별 외부 메시지 수신함을 새로 만드는 기능은 아니다.

## 저장 구조

`notification_reads`는 `(username, alert_id)`를 복합 PK로 사용한다. username은 auth_users.username, alert_id는 alert_logs.id의 FK다. read_at과 생성 시각은 UTC로 저장한다. 행이 없으면 해당 계정에서 미확인한 알림이다.

같은 알림을 여러 번 읽거나 전체 읽음과 개별 읽음 요청이 겹쳐도 한 행만 저장하고 최초 읽음 시각을 유지한다. 다른 계정의 행은 변경하지 않는다. 비밀번호 재설정이나 로그아웃으로 계정의 과거 읽음 기록을 삭제하지 않는다.

새 테이블은 [DB 마이그레이션](DB_MIGRATIONS.md)에서 생성한다. 기존 테이블을 삭제하거나 alert_logs.read_at을 덮어쓰지 않는다. 전체 PostgreSQL 데이터 이전 검증은 별도 작업이다.

## API와 인증

| API | 권한·동작 |
| --- | --- |
| `GET /api/v1/notifications` | 로그인 필요. 본인 readAt·unreadCount로 목록 반환 |
| `PATCH /api/v1/notifications/{notificationId}` | 로그인 + 본인 세션 CSRF. `{"read": true}` |
| `POST /api/v1/notifications/read-all` | 로그인 + 본인 세션 CSRF. 성공 204 |
| `GET /api/v2/monitoring/alerts` | 기존 로그인 필요. 같은 계정의 읽음 상태 반환 |

읽음 변경 시 로그인 응답의 csrfToken을 X-CSRF-Token 헤더로 보낸다. 계정 ID를 요청 본문이나 쿼리로 지정하지 않는다. 계정은 검증된 DB 세션에서만 가져온다. 비로그인·만료·로그아웃·비활성 계정은 401, CSRF 누락·불일치는 403이다. 관리자 역할이 필요한 작업은 아니다.

unreadOnly=true, 페이지·pageSize·응답 구조는 유지한다. unreadCount는 해당 계정의 전체 미확인 수이며 현재 페이지의 행 수와 다르다. 같은 시각의 알림은 ID 내림차순으로 정렬한다. 정상 알림함 응답은 Cache-Control: no-store다.

목록의 전체 건수와 본인 미확인 수는 한 번의 집계로 계산한다. 없는 페이지는200과 빈 items를 반환하고, 요청한 페이지 번호·전체 건수·본인 미확인 수는 유지한다. 비어 있거나 범위를 넘은 페이지에 불필요한 행 조회를 실행하지 않는다. 조회 중 DB 장애는503으로 응답하며 본인·다른 계정의 읽음 상태를 변경하지 않는다.

개별 읽음에 존재하지 않는 ID를 지정하면 404다. read=false로 되돌리는 API는 기존 계약에 없으며 허용하지 않는다. 읽음 쓰기 저장 실패는 내부 SQL을 노출하지 않는 503이고 전체 롤백한다.

## 전체 읽음과 기존 기록

전체 읽음은 요청의 SQL 문장에서 보이는 현재 경보를 대상으로 한다. 그 뒤 도착한 경보까지 미리 읽음으로 처리하지 않는다. 알림을 Python 메모리에 모두 읽어 처리하지 않고 INSERT SELECT와 고유 키 충돌 처리를 사용한다.

**기존 공통 read_at에는 누가 읽었는지 기록이 없으므로, 개인 읽음 행으로 복사하지 않는다.** 전환 후 개인 행이 없는 과거 알림은 각 사용자에게 미확인으로 표시된다. 과거 공통 값은 그대로 보존하며 개인 알림함과 v2 경보의 readAt에는 사용하지 않는다.

로그인 사용자는 기존 공통 경보 목록을 조회한다. 개인별 알림 노출 대상이나 수신 연락처와 로그인 계정의 연결을 임의로 추정하지 않는다. 외부 이메일/SMS 발송 여부와 화면의 읽음 여부도 별개다.

## 알림 제목

목록과 개별 읽음 응답의 제목은 저장된 `event_type`과 `severity`를 따른다. 수거 시작·완료, 측정 오류, 장비 오류, 영상 지연은 각 사건 종류로 표시한다. 수거 관련 기록은 저장된 위험도를 사용하며 고정 적재율이나 현재 임계치로 과거 기록을 다시 판정하지 않는다. 예를 들어 높은 적재율의 warning 기록도 경고로 표시하고, 장비 오류를 수거 필요 알림으로 바꾸지 않는다.

테스트 알림의 `RECORDED`는 계속 요청 기록으로 표시한다. 제목 표시만 바꾸며 기존 적재율·사건 종류·위험도·발송 상태와 읽음 기록을 수정하지 않는다.

## 검증

관리자·조회 사용자 간 분리, 개별/전체 읽음, 미확인 필터·페이지 전체 건수, 반복 요청의 최초 시각 유지, 읽음 이후 새 알림, 로그인·CSRF·세션 무효화, 계정 ID 조작, 기존 공통 읽음 보존, v2 경보 표시 일치, 저장 실패 롤백을 검증한다.

파일 DB를 다시 열고 같은 계정으로 조회했을 때 상태가 유지되는지 확인한다. 실제 Docker/Nginx에서도 두 계정으로 다르게 읽은 뒤 백엔드를 재시작해 각 계정의 시각과 미확인 개수가 유지되는지 검증한다. 운영 서버를 재배포하는 작업은 포함하지 않는다.
