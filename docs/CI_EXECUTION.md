# CI 실행과 배포 전 확인

main 대상 PR의 자동 `CI`는 Ruff 검사·포맷 검사와 mypy만 실행한다. 전체 테스트,
PostgreSQL, 이미지·배포·백업 검사는 PR 자동 실행에서 생략하며 수동 실행으로 제공한다.
main push에서는 CI를 자동 실행하지 않는다. `CI` check 이름과 CodeQL·GitHub 보호
규칙은 유지한다. 자동 CI 성공은 Ruff·mypy 성공을 의미하며 전체 검증 통과를 뜻하지 않는다.
실행 범위를 Actions 요약에 표시한다.

전체 CI는 Actions → CI → Run workflow에서 대상 브랜치를 선택해 실행한다.
main 기준 CLI 예시는 다음과 같다.

```sh
gh workflow run ci.yml --ref main
```

수동 실행에서는 기존 전체 검사를 모두 실행한다. 실행 요청과 실제 성공을 구분하고,
run의 head SHA·실제 실행 단계·완료 결과를 확인한다. 릴리스 워크플로의 검증은 유지한다.

## 배포 근거

1. 실제 main SHA와 병합 PR 최종 head를 확인한다. Git commit API의 `commit.tree.sha`로
   검증한 작업 브랜치와 실제 main의 전체 소스 tree를 대조한다. squash commit SHA가
   달라도 소스는 같을 수 있다. PR 병합 결과와 브랜치 소스가 다른 경우도 확인한다.
2. PR의 빠른 CI 성공을 전체 테스트 성공으로 사용하지 않는다. 코드 변경에는 저장소 지침에
   따른 로컬 Ruff·mypy·전체 테스트 근거를 별도로 남긴다. DB 변경에는 해당 마이그레이션과
   데이터 보존·PostgreSQL 검증 근거를 확인한다. GitHub 자동 검사를 줄이는 변경은
   로컬 검증을 완료했다고 간주하는 변경이 아니다.
3. 실제 main SHA의 CodeQL 성공을 확인한다. 전체 GitHub CI가 필요하면 수동 실행하고
   실제 결과를 기록한다. 기존 main의 전체 CI 성공은 해당 소스에 대한 근거로 유지한다.
4. 검증 대상 소스가 다르거나 근거가 부족하면 필요한 검증을 수행한다. 다른 코드나 이전
   PR의 성공을 새 변경의 결과로 표시하지 않는다.
5. 서버 반영 시 설정·DB·비밀·마운트 보존, 후보 이미지의 실제 소스 일치·격리 기동과
   반영 뒤 API·실수신 확인을 별도로 수행한다. CI 구성·문서만 변경하고 실행 코드가
   같으면 이를 이유로 서버를 재배포하지 않는다.
