# 장기간 적재율 이력 조회

`GET /api/v2/monitoring/load-history`는 로그인 세션과 명시적인 피트·장치 연결을 사용한다.
조회 기간은 최대90일, 응답은 최대1,441개 구간이다. 30일·90일과 그 사이의 사용자 지정
기간도 조회할 수 있다. 실제 데이터가 없는 과거 구간을 복원하거나0%로 채우지는 않는다.

## 요청과 집계 간격

`from`과`to`는 시간대가 포함된 ISO8601이다. 서버는 UTC로 변환하고 시작 포함·종료 제외로
조회한다. 기본 기간은 최근24시간이며 미래 종료는 기존5초 허용 범위를 유지한다.

`bucket_seconds`를 생략하면 응답 상한을 만족하는 가장 작은 간격을 선택한다.

| 기간 | 기본 선택 간격 | 구간 수 예 |
| --- | --- | --- |
| 24시간 | 60초 | 1,440~1,441 |
| 7일 | 900초 | 672~673 |
| 30일 | 3,600초 | 720~721 |
| 90일 | 7,200초 | 1,080~1,081 |

구간 수는 UTC 집계 경계와 조회 시작·끝이 맞는지에 따라 달라진다. 응답의 bucketSeconds를
그래프에 사용한다. 직접 지정할 수 있는 값은60/300/900/3600/7200/21600/86400초다.
지정한 간격으로1,441점을 초과하면 요청을 거절하며, 임의로 간격을 바꾸거나 결과를 잘라내지 않는다.
긴 기간 조회에서는 간격을 생략하거나 충분히 큰 값을 보낸다.

```http
GET /api/v2/monitoring/load-history?pit_id=pit-example&from=2026-01-01T00:00:00Z&to=2026-04-01T00:00:00Z
```

위 ID와 기간은 합성 예다. 응답 구조와 기존 필드·단위·선택 정책은 유지한다.

## 값과 결측 처리

- valuePercent는 해당 구간의 마지막 관측값이다. 마지막 관측이 무효면 이전 정상값으로 대체하지 않는다.
- compact 이력의 averagePercent/minimumPercent/maximumPercent와 유효·무효 수는 해당 구간의 보관된 scalar 표본을 집계한다.
- 계산 방식·입력 출처가 섞이면 기존처럼 MIXED/UNKNOWN과 FILL_METHOD_CHANGED_WITHIN_BUCKET을 제공한다. 서로 다른 기준의 값을 평균내지 않는다.
- 빈 구간은 NO_DATA/null이다. 과거 표본의 유효성은 원래 관측 시각과 근거를 사용한다.
- 과거 세부 metadata가 없으면 시각·관측ID를 추정하지 않는 기존 nullable 처리를 유지한다.
- 구간 경계는 실제 from/to로 자르며, 초의 소수 부분도 유지한다. 평균값으로 마지막 측정값이나 실제 측정 시각을 바꾸지 않는다.

## 조회 비용 제한

일반 STATE는 기존 SQL 순위 집계로 구간당 마지막 원문만 가져온다. PostgreSQL compact
이력은 기존 현장·장치·시간 복합 기본키로 범위를 제한하고512행씩 순차 수신한다. DB에서
큰 JSON을 펼쳐 정렬하지 않는다. 읽은 순서와 무관하게 같은 구간 통계를 계산한다.
수신 묶음을 늘려 커서의 반복 통신을 줄이며, 한 번에 해석하는 버퍼는 커진다.
버퍼는 분 원문의 크기에 영향을 받지만 전체 조회 기간을 한꺼번에 적재하지 않는다.

완전히 포함된 분은 기록 당시 저장한 valid_count/invalid_count/sum/minimum/maximum을
확인해 사용한다. 과거 형식에 통계가 없으면 그 분의 scalar에서 계산한다. 실제 유효 표본의
출처·방법을 확인해 MIXED를 유지한다. 구간별 출처·방법은 혼합 여부를 판별할2종까지만
보관하고, metadata도 선택한 마지막 표본만 남긴다. 메모리에 전체 기간의 분 원문을 쌓지 않는다.

시작·끝의 일부만 선택된 분은 원래 표본 시각으로 검사해 microsecond 경계를 유지한다.
늦게 도착한 과거 표본이 분의 last를 덮어써도 실제 최대 표본 시각을 선택한다. SQLite는
기존 SQL 집계 경로를 유지한다. 새 테이블·인덱스나 측정 기록 변경은 필요하지 않다.

PostgreSQL 이력 조회에는20초 처리 상한을 적용한다. DB 설정은 현재 트랜잭션에만 적용하고
commit/rollback 후 원복한다. 서버 커서도 취소·오류 때 닫는다. 상한을 넘으면503
HISTORY_QUERY_TIMEOUT을 반환하며 빈 그래프나0% 정상 데이터로 대신하지 않는다.

SQL은 요청 범위의 보관된 scalar를 처리하므로 긴 기간의 비용 자체가0이 되지는 않는다.
응답 상한은 브라우저에 돌려주는 구간 수이며 보관된 원본 데이터 수의 상한은 아니다.
응답 시간은 실제 보관된 분과 표본 수, JSON 크기, DB 캐시와 동시 부하에 영향을 받는다.
30일과90일이 같은 보관 데이터를 포함할 수도 있으므로 기간에 정비례하지 않는다.
20초는 조회 처리의 제한이며 성공 응답을 보장하는 시간이 아니다. 연결·인증·응답 전송을
포함한 클라이언트의 왕복 시간은 별도다. 수신 묶음 조정 후에도 제한 시간 초과 가능성은 남는다.

## 422 오류

- HISTORY_TIMEZONE_REQUIRED: 시간대가 없는 시각.
- HISTORY_TIME_OUT_OF_RANGE: 시각 변환 범위 초과.
- HISTORY_FUTURE_RANGE: 허용 범위를 넘는 미래 종료.
- HISTORY_RANGE_MUST_BE_WITHIN_90_DAYS: 역순·빈 기간 또는90일 초과.
- HISTORY_TOO_MANY_POINTS: 지정한 간격으로 응답 상한 초과.
- 허용되지 않는 bucket_seconds는 요청 필드 검증 오류.

오류 본문은 기존 [응답 명세](DASHBOARD_RESPONSE_CONTRACT.md)를 따른다. 이 변경은 장기 조회
지원이며 센서·입력 상태에 따른 판단불가 표시를 강제로 정상으로 바꾸는 기능은 아니다.

503 HISTORY_QUERY_TIMEOUT이면 새로고침을 무한 반복하지 말고 기간을 줄여 다시 조회한다.
