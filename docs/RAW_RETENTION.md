# 스캔 원문 보관 기간과 자동 정리

보관 기간 기본값은 **30일**이다. `EDGE_V2_RAW_RETENTION_DAYS` 하나로 14일·7일 등으로
바꿀 수 있으며 코드 수정이나 이미지 재빌드는 필요하지 않다. 자동 정리는 명시적으로 활성화한다.

| 설정 | 기본값 | 역할 |
| --- | --- | --- |
| `EDGE_V2_RAW_RETENTION_ENABLED` | `false` | 자동 정리 및 명시적 쓰기 작업 허용. compact 저장 필요 |
| `EDGE_V2_RAW_RETENTION_DAYS` | `30` | 보관 기간. 1~3650일 |
| `EDGE_V2_RAW_RETENTION_BATCH_SIZE` | `100` | 테이블별 한 배치 최대 대상 수. 1~1000개 |
| `EDGE_V2_RAW_RETENTION_INTERVAL_SECONDS` | `3600` | 한 순회 완료 후 다음 순회 대기. 60~86400초 |

```dotenv
EDGE_V2_COMPACT_STORAGE_ENABLED=true
EDGE_V2_RAW_RETENTION_ENABLED=true
EDGE_V2_RAW_RETENTION_DAYS=30
```

14일 또는 7일로 줄일 때는 마지막 값만 각각 `14`, `7`로 바꾼다. Docker 환경변수를
바꾸면 수정한 설정으로 컨테이너를 재생성해야 반영된다. 단순 `docker restart`는 새
환경변수를 주입하지 않는다. 기간을 줄이면 다음 정리 범위가 넓어지므로 먼저 대상을 확인한다.
기간을 다시 늘려도 이미 정리한 원문은 돌아오지 않는다.

## 정리 범위

행 전체를 삭제하지 않고 다음 원문만 작은 만료 표시로 대체한다.

- `scan_source`·원문을 보관한 `scan_result` artifact 본문.
- 과거 `lidar_measurement` 접수 본문. ID·원래 접수 시각·내용 해시는 유지한다.
- 과거 STATE 판정의 선택적 `filtered_point_clouds`만 제거한다. 나머지 판정 내용·적재율·단면 결과는 유지한다.

현재 관측의 `edge_v2_latest`와 필터 창, 알림·수거 EVENT·분 집계·상태 전이 이력,
설정·보정 자료는 정리하지 않는다. 최신 투영이 참조하는 접수와 설정된 장비의 마지막 원문도
보호한다. 재수신 ACK와 불변 artifact 충돌 확인에 사용하는 식별·해시는 유지한다.
옛 artifact에 내용 해시가 없다면 원문을 대체하기 전에 원래 해시부터 보존한다.

개별 artifact는 스캔 취득 시각 또는 STATE 생성 시각, 접수 본문은 원래 수신 시각으로
기간을 계산한다. **UTC의 완료된 날짜 단위**로 정리해 설정 기간보다 먼저 지우지 않는다.
30일 설정은 최소 30일을 보관하며 날짜 경계와 분할 처리 때문에 실제 정리까지 추가 시간이
걸릴 수 있다. 시각이 없거나 해석할 수 없는 원문은 자동으로 지우지 않는다.

원문 보관 기간은 계산용 최신성 1초, 화면 유지 3초, 운영 지연 경고 3초,
최근 5초 중앙값, 손실 경고 정상 1시간 복귀와 별개이며 그 판정 기준을 변경하지 않는다.

## 미리보기와 수동 실행

명시적 DB migration을 마친 환경에서 실행한다. DB 주소·자격 증명은 비공개 환경으로
제공하고 명령행이나 로그에 넣지 않는다.

```bash
uv run python -m src.app.cli.raw_retention --dry-run
```

기본은 읽기 전용이다. 테이블별 최대 한 배치의 대상 수·건너뛴 시각 오류·완료 여부만 JSON으로
출력하며 원문·개인정보·인증값은 출력하지 않는다. **한 배치 결과는 DB 전체 대상 수나 예상 확보
용량이 아니다.** 여러 배치를 확인하려면 `--max-batches 10`처럼 지정한다.

실제 정리 설정을 명시적으로 활성화한 경우에만 쓰기 모드를 사용할 수 있다.

```bash
uv run python -m src.app.cli.raw_retention --apply --max-batches 1
```

명령 성공은 처리한 배치의 커밋 결과이며 전체 저장소 정책 적용 완료를 뜻하지 않는다.

## 적용과 DB 변경

1. 원본·설정·계정·비밀 파일을 보존하고 검증한 백업과 복원 준비를 확인한다.
2. 기본값 `EDGE_V2_RAW_RETENTION_ENABLED=false`를 유지하며 새 이미지를 준비한다.
3. migration 계정으로 `python -m src.app.cli.db upgrade`와 `check`를 실행한다.
   Alembic `0007_raw_retention`은 조회용 보조 인덱스만 추가하며 기존 원문을 지우지 않는다.
4. 미리보기로 기간과 보호 대상을 검토한 뒤 자동 정리를 활성화해 컨테이너를 재생성한다.
5. 서비스와 `RAW_RETENTION_BATCH`·`RAW_RETENTION_FAILED`, 실제 DB·디스크 사용량을 확인한다.

업그레이드 CLI는 이전 구조 변경을 `0006`까지 먼저 커밋하고 `0007` 적용을 별도 단계로 처리한다.
PostgreSQL의 기존 DB에서는 그 사이에 트랜잭션 밖에서 보조 인덱스를 `CONCURRENTLY`로 준비한다.
전체 업그레이드가 한 트랜잭션으로
되돌려지는 절차는 아니다. 준비가 실패해도 이전 커밋과 데이터는 보존하며 원인을 확인한 뒤
같은 명령을 재실행한다. 마이그레이션 운영자는 한 명으로 정한다.
새 DB나 이미 구조 변경 잠금을 가진 초기 업그레이드에서는 그 트랜잭션 안에서 인덱스를 만든다.
DB API를 직접 사용하는 도구도 데이터가 있는 PostgreSQL에서 트랜잭션 밖의 인덱스 준비를 수행해야 한다.

백그라운드 작업은 한 배치를 커밋한 뒤 다음 배치 사이에 대기한다. PostgreSQL에서는 다른
정리 작업이 잠근 행을 건너뛴다. 종료·취소 시 미완료 배치를 롤백하고 재시작하면 남은 대상을
다시 확인한다. 단일 인스턴스·Uvicorn worker 1개라는 기존 배포 전제를 유지한다.
만료된 원문을 복원할 수 있는 자동 downgrade는 제공하지 않는다.

## 디스크 관리와 구분

원문을 만료해도 접수·불변성 해시·이력·인덱스는 누적된다. **전체 DB 크기를 고정하거나
디스크 부족을 모두 해결하는 기능은 아니다.** PostgreSQL에서 원문을 제거한 공간은 재사용될 수
있지만 OS에서 보이는 파일 크기가 즉시 줄어들지는 않는다. 자동 `VACUUM FULL`, 전체 테이블 삭제,
이미지 정리나 백업 삭제는 수행하지 않는다.

정기 백업 보관 개수·외부 저장소·디스크 사용률 경고와 대응 담당은 별도로 관리한다.
영상 보관 기간은 미디어 서비스 담당 범위이며 이 설정으로 바뀌지 않는다.
기능 코드 검증, 서버에서 설정을 반영한 사실, 실제 원문 정리 결과는 각각 구분해 기록한다.
