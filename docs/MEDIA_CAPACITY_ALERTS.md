# 미디어 용량 정리 상태 운영 메일

미디어의 `GET /api/v2/capacity-cleanup/status`를 읽어 기존 Gmail 운영 채널로 통보한다.
GET은 정리·재시도·인코딩을 실행하지 않으며 백엔드 관측 작업도 삭제를 수행하지 않는다.
웹 앱·업무 DB·업무 알림 수신자 API와 분리된 운영 CLI다. 새 화면이나 삭제 실행 API는 없다.

## 기존 설정과 분리

`server-capacity-alerts.txt`의 기존 `enabled`, 수신자, 서버 이름을 읽는다.
파일 형식과 디스크75/90 기준·현재 디스크 점검 작업·기존 상태 파일은 변경하지 않는다.
미디어 상태에는 별도 비공개 상태 파일과 단일 실행 잠금을 사용한다.
`MEDIA_SERVICE_URL`/선택적 `MEDIA_DAILY_SERVICE_URL`과 기존 게이트웨이 인증을 재사용하며
`MEDIA_AUTH_MODE=internal`로 자동 전환하지 않는다. 별도 토큰·수신자를 만들지 않는다.

현재 상태 응답의 다음 값을 구분한다.

- 미디어 정책: 기본 보관30일, 정리 시작90/해제85/긴급95는 미디어의 설정이다.
  기본30일은 최소 보장 기간이 아니며 백엔드가 이 값을 덮어쓰지 않는다.
- `critical`/`alert_latched`: 긴급 진입과85% 회복까지 유지되는 구간.
- `blocked`/`suspended`/`error`, 정체 및 정리 불가 사유: 긴급 압박률 아래여도 통보한다.
- 최신성·조회 오류·비활성·잘못된 정책: 상태 확인 불가이며 정상 복구가 아니다.
- 파일 정리 완료 건수와 관측된 공간 회수 순증가·최근 회수 확인: 서로 다른 값이다.

## 최신성·중복 억제·복구

상태 JSON은64KiB 이내이며 기존 전역 미디어8MiB 보호도 유지한다.
리다이렉트와 캐시 응답, 잘못된 타입·압박률·UTC 시각은 정상 상태로 수용하지 않는다.
`state_fresh`뿐 아니라 서버의 현재 시각으로 `observed_at`/`valid_until_at`을 검사하고,
유효 창이 미디어의 `2×interval_seconds+10초`를 초과하면 거부한다.

상태 확인, 용량 긴급, 정리 불가의 세 채널을 독립적으로 기억한다.
상태가 오래되면 상태 확인 채널만 통보하며 기존 긴급·정리 불가를 해제하지 않는다.
조회 복구 메일은 공간 회복을 의미하지 않는다. 알려진 긴급 구간은 최신 응답에서
관련 한도 모두 stop 기준 이하임을 확인하기 전에는 잃어버린 upstream latch만으로 해제하지 않는다.

정상 최초 시작에는 메일을 보내지 않는다. 신규 긴급/정리 불가, 사유 변경 및 회복은
구분하여 통보한다. 같은 운영 상태 반복은 미디어 `policy.notification_seconds`를 따르며,
상태 확인 불가의 반복은 기존 운영 설정 `reminder_seconds`를 따른다.
미디어의 `notification_sequence`는 메일 본문의 관측 근거로 남긴다.

수신자별 해시·상태·시도 시각·메일 식별자만 별도0600 파일에 보관한다.
발송 전 PENDING을 원자 저장·fsync한다. ACCEPTED는 Gmail 접수이며 수신함 도착과 별개다.
PENDING/UNKNOWN은 같은 알림 구간에서 무조건 재발송하지 않는다. 명시적 거절만 대기 후
재시도하며 상태 파일을 삭제해 재발송시키지 않는다. 상태가 손상됐거나 쓸 수 없으면 발송하지 않는다.

## 실행

전용 상태 디렉터리는 운영자가0700으로 먼저 준비한다. 기존 디스크 상태 경로를 재사용하지 않는다.
아래는 공개 예제 경로다. 실제 주소·인증·설정 파일은 비공개로 주입한다.

```sh
# 기본은 제한된 GET 조회만 한다. 상태 저장·발송 의도를 소비하지 않는다.
uv run python -m src.app.cli.media_cleanup_alerts \
  --config private-access/server-capacity-alerts.txt \
  --state private-access/media-cleanup-state/state.json

# 승인된 운영 서비스에서만 명시적으로 활성화한다.
# 위 명령에 --send --loop --interval-seconds 30 추가
```

조회 간격은 CLI의 `--interval-seconds`로5~3600초를 지정한다. 기본30초다.
운영 설정 파일은 매 순회 읽으며, 미디어 자체의 정리 주기와 알림 반복 주기는 응답 정책을 따른다.
Gmail 인증 파일은 기존 send-only 파일을 읽기 전용으로 재사용한다.
가능하면 독립 컨테이너에 미디어 접속용 환경과 필요한 읽기 전용 설정/인증,
전용 상태 쓰기 마운트만 제공한다. 업무 DB·미디어 영상 디렉터리의 쓰기 권한은 필요하지 않다.

미디어 상태와 실패 사유만 확인하며 운영 영상 삭제·임계값 하향·테스트 메일로 기능을 시험하지 않는다.
가짜 발송기/격리 미디어 응답으로 중복 억제·긴급·정체·실패·복구를 검증하고,
실제 환경에서는 정상 상태의 제한 조회와 설정·프로세스 보존을 구분해 확인한다.
정책 구현, 서버 활성, 자연스러운 최초 삭제·실제 공간 회수·녹화 지속은 각각 별도 완료 단계다.

## 날짜 녹화 삭제 사유

날짜 전체/요약 응답은 선택적인 `deletion_reason=capacity_pressure`를 보존한다.
기존 자료에서 사유가 없으면 필드를 생략한다. deleted/expired, deleted_at, cleanup 상태와
재생/다운로드/exports410, revision/커서, 생략 배열 의미는 기존대로 유지한다.
용량 정리를 시간 만료나 촬영 누락 없음으로 치환하지 않는다.
