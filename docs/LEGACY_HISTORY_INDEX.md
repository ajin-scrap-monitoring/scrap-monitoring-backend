# 과거 원문 이력 인덱스 축소

`0009_legacy_history_index`는 `ix_v2_legacy_history`를 실제 과거 원문 이력 조회 조건인
`compact IS FALSE`에 해당하는 행만 포함하도록 바꾼다. 같은 열 순서와 인덱스 이름을 유지한다.
compact 저장의 이력은 기존 분 요약 조회를 그대로 사용한다.

접수 행·ID·원문·내용 해시·고유 제약·상태 sequence·설정·보정·경보·수거·분 이력은 변경하지
않는다. 원문30일 보관이나 영구 중복·충돌 검증 계약을 바꾸지 않는다. 이 최적화만으로 DB 전체
증가가 멈추지는 않으며, 행 보관 정책을 대신하지 않는다. 적용 전 인덱스 크기와 실제 적용 후
크기를 비교해야 한다. 행 비율만으로 확보 바이트를 보장하지 않는다.

## 적용

기존 [DB migration 절차](DB_MIGRATIONS.md)를 따른다. 자격 증명은 비공개 환경에서
제공하고 명령행이나 로그에 넣지 않는다. 앱 계정의 권한을 임의 확대하지 않는다.

```bash
uv run python -m src.app.cli.db current
uv run python -m src.app.cli.db upgrade
uv run python -m src.app.cli.db check
```

PostgreSQL의 명시적 upgrade는 필요한 기존 구조 변경을 버전8까지 커밋하고, 별도 AUTOCOMMIT
연결에서 새 인덱스를 CONCURRENTLY로 먼저 만든다. 기존 인덱스는 준비 중 유지한다. 준비는
전용 세션 잠금으로 한 작업자만 수행하고, 유효한 준비 인덱스는 재실행해도 다시 만들지 않는다.
이 버전이 소유한 정의의 무효 준비 인덱스만 다시 만들 수 있다. 이름이 같아도 다른 테이블·열·
조건·고유성·접근 방식이면 교체하지 않고 실패한다. 준비에는 추가 디스크 공간과 I/O가 필요하다.

새 인덱스의 정의와 유효성이 확인된 다음 버전9 트랜잭션에서 기존 보조 인덱스를 교체하고
revision을 함께 커밋한다. 교체의 잠금 대기는5초로 제한한다. 실패하면 교체와 revision 변경이
롤백되어 기존 인덱스가 남고, 준비된 새 인덱스는 재시도에 재사용할 수 있다. 동시 실행 중인
운영 조회·migration과의 충돌이 반복되면 원인을 확인한 후 새 적용 시간을 정한다.

새 DB 또는 현재 migration이 이미 테이블 쓰기/구조 잠금을 가진 경우에는 해당 트랜잭션 안에서
인덱스를 준비할 수 있다. 데이터가 있는 PostgreSQL에서 직접 Alembic 호출만으로 긴 일반
CREATE INDEX를 실행하지 않고 위 CLI로 별도 준비를 수행한다. SQLite는 migration 트랜잭션에서
보조 인덱스를 다시 만든다. 기존 스키마 버전8까지 끝난 작업을 처음부터 재적용하지 않는다.

실제 서버 반영은 검증된 새 이미지와 버전9를 함께 준비하고 수행한다. 새 버전 검사에 맞는
이미지를 사용하며 단순히 옛 이미지로 되돌려 버전 검사 오류를 만들지 않는다. 자동 downgrade,
데이터 삭제, VACUUM FULL, 백업·영상 삭제는 제공하지 않는다. 보존·복구 절차는 기존 운영
정책을 유지하며 이미 끝난 백업 다운로드·복원 작업을 반복하지 않는다.

## 확인 범위

- SQLite와 PostgreSQL에서 기존 접수 모든 열 및 이력 결과·중복 고유키 보존.
- PostgreSQL 일반 prepared plan에서도 `compact IS FALSE` 조건의 결과 보존.
- 유효한 준비 인덱스 재사용, 정의가 다른 준비 인덱스 차단.
- 기존 동시 수신·원문 만료·적재율 이력·상태 조회 회귀 검증.
- 실제 운영의 준비 소요 시간·공간 절감·I/O 영향은 별도 적용 결과로 기록.
