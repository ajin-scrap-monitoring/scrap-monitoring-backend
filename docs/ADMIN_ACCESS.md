# 관리자 설정 API 접근 권한

계정·세션은 [로그인 DB 저장 안내](AUTH_STORAGE.md)를 따른다. 브라우저 화면에서 관리자 메뉴를 숨기는 것과 별개로, 아래 API는 요청마다 DB 세션과 현재 역할을 검사한다. 설정 화면의 알림 수신 대상은 로그인 계정과 별도 데이터다.

## 권한 범위

| API | 조회 계정 | 관리자 | 변경 시 CSRF |
| --- | --- | --- | --- |
| `GET /api/v1/settings/alerts` | 불가 | 가능 | 불필요 |
| `PUT /api/v1/settings/alerts` | 불가 | 가능 | 필수 |
| `GET /api/v1/notification-recipients` | 불가 | 가능 | 불필요 |
| `POST /api/v1/notification-recipients` | 불가 | 가능 | 필수 |
| `PATCH /api/v1/notification-recipients/{recipientId}` | 불가 | 가능 | 필수 |
| `POST /api/v1/notifications/test` | 불가 | 가능 | 필수 |
| `GET /api/v1/config/pits` | 가능 | 가능 | 불필요 |
| `GET /api/v1/config/pits/{pit_id}` | 가능 | 가능 | 불필요 |
| `PUT /api/v1/config/pits/{pit_id}` | 불가 | 가능 | 필수 |

모든 경로는 로그인 쿠키가 필요하다. 피트 설정 조회는 모니터링 화면에서도 사용할 수 있으므로 조회 계정에 허용한다. 관리자 설정과 알림 수신 연락처 조회는 관리자만 가능하다. 정상 응답은 `Cache-Control: no-store`로 반환한다.

## 프론트엔드 요청

1. 기존 `POST /api/v1/session`으로 로그인한다. 로그인 성공 응답의 `csrfToken`을 보관한다.
2. API 요청에 `scrap_session` 쿠키를 포함한다. 같은 출처를 사용하는 것이 기본이며, 다른 출처에서 호출할 때는 쿠키 전송과 서버 CORS 설정을 맞춘다.
3. 설정 변경·수신 대상 등록/변경·테스트 알림 요청은 `X-CSRF-Token: <로그인 응답의 csrfToken>` 헤더를 추가한다.
4. 경보 설정 PUT에는 최신 GET 응답의 ETag를 `If-Match`로 반드시 전달한다. 요청·응답 필드와 API 경로는 유지한다. CSRF 토큰과 ETag는 다른 목적이며 서로 대신할 수 없다.
5. 수신 대상 PATCH에는 목록의 해당 수신자 `version` 또는 생성/수정 응답 ETag를 `If-Match`로 전달한다. 제공된 버전이 오래됐거나 저장 중 다른 요청이 먼저 변경하면 `412`로 거절한다. 기존 헤더 없는 호출은 호환성을 위해 유지하지만 대시보드는 항상 버전을 전달한다.

CSRF 토큰은 같은 세션에서 받은 값을 사용한다. 새로 로그인했으면 새 값을 사용하며, 다른 관리자 세션의 토큰도 거절한다. 관리자 역할은 클라이언트가 전달한 값으로 판단하지 않는다.

## 실패 처리

- `401`: 쿠키 없음·유효하지 않은 세션·만료·로그아웃·비활성 계정. 로그인 화면으로 안내한다.
- `403`: 관리자 권한 없음 또는 CSRF 토큰 누락·불일치. 변경을 재시도하기 전에 권한과 현재 세션을 확인한다.
- `428`: 경보 설정 PUT의 If-Match 누락. 최신 설정과 ETag를 먼저 조회한다.
- `412`: 경보 설정 또는 수신 대상 버전 불일치. 최신 목록/설정을 다시 조회한 후 사용자에게 변경 내용을 확인받는다. 오래된 본문을 자동 재전송해 덮어쓰지 않는다.
- 인증 저장소 장애는 기존 세션 검사에 따라 `503`이다.

검사에 실패한 요청은 해당 API의 설정 조회·기본 피트 생성·수신 대상 변경·테스트 알림 기록 단계까지 진행하지 않는다. DB에서 관리자 역할을 조회 역할로 바꾸거나 계정을 비활성화하면 기존 쿠키에도 다음 요청부터 반영된다.

## 검증 범위

미로그인 접근, 조회 계정의 관리자 정보 조회·변경, 관리자 CSRF 누락·오류·다른 세션 토큰, 만료·로그아웃·비활성화·역할 변경을 검증한다. 차단 시 업무 데이터가 생성되지 않는지도 확인한다. 기존 설정 변경·수신 대상 처리·ETag·피트 생성/조회 테스트는 실제 로그인과 CSRF 헤더를 사용해 유지한다.

이번 작업은 위 관리자·설정 API의 접근 검사다. 모든 v1 모니터링·이력 API의 인증 정책 변경, 사용자 등록·계정 관리 화면 및 외부 이메일/SMS 실제 발송 기능은 포함하지 않는다.
