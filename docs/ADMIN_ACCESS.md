# 관리자 설정 API 접근 권한

계정·세션은 [로그인 DB 저장 안내](AUTH_STORAGE.md)를 따른다. 브라우저 화면에서 관리자 메뉴를 숨기는 것과 별개로, 아래 API는 요청마다 DB 세션과 현재 역할을 검사한다. 설정 화면의 알림 수신 대상은 로그인 계정과 별도 데이터다.

## 권한 범위

| API | 조회 계정 | 관리자 | 변경 시 CSRF |
| --- | --- | --- | --- |
| `GET /api/v1/settings/alerts` | 불가 | 가능 | 불필요 |
| `PUT /api/v1/settings/alerts` | 불가 | 가능 | 필수 |
| `GET /api/v1/notification-recipients` | 불가 | 가능 | 불필요 |
| `POST /api/v1/notification-recipients` | 불가 | 가능 | 필수 |
| `PATCH /api/v1/notification-recipients/{recipientId}` | 불가 | 가능 | 필수 |
| `POST /api/v1/notifications/test` | 불가 | 가능 | 필수 |
| `GET /api/v1/config/pits` | 가능 | 가능 | 불필요 |
| `GET /api/v1/config/pits/{pit_id}` | 가능 | 가능 | 불필요 |
| `PUT /api/v1/config/pits/{pit_id}` | 불가 | 가능 | 필수 |

모든 경로는 로그인 쿠키가 필요하다. 피트 설정 조회는 모니터링 화면에서도 사용할 수 있으므로 조회 계정에 허용한다. 관리자 설정과 알림 수신 연락처 조회는 관리자만 가능하다. 정상 응답은 `Cache-Control: no-store`로 반환한다.

## 프론트엔드 요청

1. 기존 `POST /api/v1/session`으로 로그인한다. 로그인 성공 응답의 `csrfToken`을 보관한다.
2. API 요청에 `scrap_session` 쿠키를 포함한다. 같은 출처를 사용하는 것이 기본이며, 다른 출처에서 호출할 때는 쿠키 전송과 서버 CORS 설정을 맞춘다.
3. 설정 변경·수신 대상 등록/변경·테스트 알림 요청은 `X-CSRF-Token: <로그인 응답의 csrfToken>` 헤더를 추가한다.
4. 경보 설정 PUT에는 최신 GET 응답의 ETag를 `If-Match`로 반드시 전달한다. 요청·응답 필드와 API 경로는 유지한다. CSRF 토큰과 ETag는 다른 목적이며 서로 대신할 수 없다.
5. 수신 대상 PATCH에는 목록의 해당 수신자 `version` 또는 생성/수정 응답 ETag를 `If-Match`로 전달한다. 제공된 버전이 오래됐거나 저장 중 다른 요청이 먼저 변경하면 `412`로 거절한다. 기존 헤더 없는 호출은 호환성을 위해 유지하지만 대시보드는 항상 버전을 전달한다.

CSRF 토큰은 같은 세션에서 받은 값을 사용한다. 새로 로그인했으면 새 값을 사용하며, 다른 관리자 세션의 토큰도 거절한다. 관리자 역할은 클라이언트가 전달한 값으로 판단하지 않는다.

수신 대상 PATCH에서 생략한 필드는 기존 값을 유지한다. 전화번호를 삭제하려면 `{"phone": null}`을 보내며, 다른 필드의 null은 허용하지 않는다. 빈 요청·알 수 없는 필드·빈 이름/팀·빈 채널 목록·중복 채널/이벤트 유형은 `422`로 거절하고 기존 값과 버전을 유지한다. `enabled=false`와 빈 사용자 지정 `eventTypes` 목록은 유효한 수정 값이다.

## 실패 처리

- `401`: 쿠키 없음·유효하지 않은 세션·만료·로그아웃·비활성 계정. 로그인 화면으로 안내한다.
- `403`: 관리자 권한 없음 또는 CSRF 토큰 누락·불일치. 변경을 재시도하기 전에 권한과 현재 세션을 확인한다.
- `428`: 경보 설정 PUT의 If-Match 누락. 최신 설정과 ETag를 먼저 조회한다.
- `412`: 경보 설정 또는 수신 대상 버전 불일치. 최신 목록/설정을 다시 조회한 후 사용자에게 변경 내용을 확인받는다. 오래된 본문을 자동 재전송해 덮어쓰지 않는다.
- `422`: 수정할 값이 없거나 수신 대상 입력값이 유효하지 않음. 입력을 수정한 후 재요청한다.
- 인증 저장소 장애는 기존 세션 검사에 따라 `503`이다.

인증·권한 검사에 실패한 요청은 해당 API의 설정 조회·기본 피트 생성·수신 대상 변경·테스트 알림 기록 단계까지 진행하지 않는다. DB에서 관리자 역할을 조회 역할로 바꾸거나 계정을 비활성화하면 기존 쿠키에도 다음 요청부터 반영된다.

## 수신 대상 입력과 동시 저장

수신 대상 등록·수정은 DB 저장 전에 다음 길이를 검증한다. 초과하면422로 응답하며 기존 값과 버전은 유지한다.

| 항목 | 최대 길이 |
| --- | --- |
| 이름·소속 | 각각100자 |
| 이메일 | 255자 |
| 전화번호 | 50자 |

채널과 이벤트 유형의 중복 선택도422다. 전화번호의null 초기화와 생략 시 기존 값 유지는 동일하다.

같은 이메일을 동시에 등록하거나 서로 다른 수신자가 같은 이메일로 동시에 변경하면 한 요청만 저장하고 나머지는409로 응답한다. 거절된 변경은 기존 값과 버전을 유지한다. 최신 버전 충돌의412 응답은 그대로 유지한다. 다른 DB 무결성 오류를 이메일 중복으로 처리하지 않는다.

## 설정 입력의 저장 범위

알림 설정의 `sendDelayMinutes`·`repeatIntervalMinutes`는0~2147483647, `maximumRepeatCount`는1~2147483647 범위를 허용한다. DB에 저장 가능한 정수 범위이며 새로운 알림 주기나 실제 발송 정책을 정한 값은 아니다. 범위를 넘으면503 대신422로 거절하고 기존 임계치·정책·ETag를 유지한다.

피트 ID는 최대50자, 이름은 최대100자다. 깊이 `total_depth_cm`는 양수이면서 유한한 cm 값이어야 한다. `Infinity`·`NaN`과 숫자 표현 범위를 넘는 값은 저장하지 않는다. 깊이 생략 또는null은 기존처럼 현재 값을 유지한다.

비유한 숫자가 포함된 입력 오류도 유효한 JSON422로 응답한다. 오류 상세의 `input`·`ctx`에 포함된 비유한 숫자만 `inf`·`-inf`·`nan` 문자열로 표현하며, 일반 입력 오류 응답 형식은 유지한다.

## 임계치 저장 조건

경보 설정과 피트 설정은 기존 판정기가 사용할 수 있는 조합만 저장한다. 사전 경보 임계치는 `수거 경보 임계치 - 5%p` 이하여야 한다. 예를 들어 수거90%이면 사전 경보85%는 허용하고89%는422로 거절한다. 수거 임계치는 최소5%이며, 사전 경보0%·수거5%와 사전 경보95%·수거100%도 유효하다.

사전 경보 표시를 끈 경우에도 같은 조건을 적용한다. 표시 여부와 별개로 판정기는 이 임계치로 상태를 구분하기 때문이다. 잘못된 설정은 기존 임계치·정책·ETag를 바꾸지 않는다. 피트 설정에서 한쪽 임계치만 보낼 때는 저장된 다른 쪽 값과 함께 검증하고, 새 피트이면 기본값과 함께 검증한다. PostgreSQL에서는 잠근 최신 피트 값을 사용해 다른 관리자의 동시 수정도 반영한다.

정상적으로 저장한 임계치는 다음 유효한 측정의 판정에 적용한다. 사전 경보 표시를 꺼도 수거 필요 경보까지 꺼지지는 않는다. 기존5%p 복귀 조건과30분 알림 쿨다운은 유지하며, 설정 저장은 외부 이메일·문자 발송 완료를 의미하지 않는다.

## 테스트 알림 접수와 실제 발송

`POST /api/v1/notifications/test`는 현재 외부 발송 없이 테스트 요청을 기록한다. `202`와 `status=accepted`는 요청 접수이며 이메일·문자 발송 성공을 뜻하지 않는다. 새 기록은 `RECORDED`/`info`와 실제 발송을 수행하지 않았다는 메시지를 사용하고, 알림 목록에는 `테스트 알림 요청 기록`으로 표시한다. 선택한 채널은 요청 내용으로 남는다.

기존 `SENT` 기록은 이 변경에서 수정하지 않는다. 실제 외부 발송과 성공·실패 결과 처리는 별도 연동이 필요하며, SMTP 설정만 추가해도 이 테스트 API가 이메일을 보내는 것은 아니다.

## 검증 범위

미로그인 접근, 조회 계정의 관리자 정보 조회·변경, 관리자 CSRF 누락·오류·다른 세션 토큰, 만료·로그아웃·비활성화·역할 변경을 검증한다. 차단 시 업무 데이터가 생성되지 않는지도 확인한다. 기존 설정 변경·수신 대상 처리·ETag·피트 생성/조회 테스트는 실제 로그인과 CSRF 헤더를 사용해 유지한다.

이번 작업은 위 관리자·설정 API의 접근 검사다. 모든 v1 모니터링·이력 API의 인증 정책 변경, 사용자 등록·계정 관리 화면 및 외부 이메일/SMS 실제 발송 기능은 포함하지 않는다.
