# 서버 관리자 용량 알림

대시보드와 업무 DB를 사용하지 않는 운영 전용 점검 작업이다. 서버 관리자 주소와
경고 기준은 `private-access/server-capacity-alerts.txt`에서 관리한다. 기존 관리자 수신자
API·operationsEmailEnabled·업무 알림·원문 보관 정책은 변경하지 않는다. 자동 삭제는 없다.

## 비공개 TXT 설정

`deploy/disk-alerts/server-capacity-alerts.example.txt`는 실제 주소가 없는 형식 예제다.
실제 파일은 Git에서 제외하고 0600 권한으로 저장한다. 기존 인증 파일을 덮어쓰지 않는다.

```ini
[monitor]
enabled = false
server_name = backend-server
recipients =
warning_percent = 75
critical_percent = 90
interval_seconds = 300
reminder_seconds = 3600

[disk:system]
path = /
require_mount = true
```

`recipients`에는 쉼표로 나누거나 다음 줄을 들여써서 메일 주소를 지정한다.
발송 활성화에는 주소와 `enabled = true`, 명령의 `--send`가 모두 필요하다.
서버 이름과 disk 이름은 영문·숫자·밑줄·하이픈을 사용한다. 주소·기준·경로는 운영자 설정이다.

경고는75%, 긴급은90%가 초기값이다. `warning_percent`와 `critical_percent` 두 숫자만
수정하면 실행 중인 `--loop`가 다음 점검 때 파일을 다시 읽는다. 재시작이 필요 없으며
기본5분 주기에서 반영까지 최대 약5분과 기존 점검 처리 시간이 걸릴 수 있다.
`0 < warning_percent < critical_percent <= 100`을 만족해야 한다.

경계에서 반복 알림이 발생하지 않도록 정상 복귀는 경고 기준에서5%p를 뺀 값(최소0),
긴급 해제는 긴급 기준에서 `min(5, 두 기준 차이/2)`%p를 뺀 값으로 자동 계산한다.
기본75/90에서는70% 이하 정상,85% 이하 긴급 해제이다. 필요하면 선택 항목
`recovery_percent`, `critical_recovery_percent`로 명시하되 순서를 유지한다.
이 기준은 서버 용량 전용이며 센서 손실 경고의 정상1시간 복귀 기준과 무관하다.

## 실행과 상태 보존

호스트에서 실행하거나, 관측할 파일시스템을 읽기 전용으로 연결한 별도 컨테이너에서
실행한다. 백엔드 컨테이너 내부의 임의 경로가 DB·미디어 파일시스템을 가리킨다고
가정하지 않는다. `path`는 실제 점검할 마운트 지점으로 지정하고, 같은 파일시스템을
중복 등록하지 않는다. 별도 파일시스템이면 `[disk:media]` 같은 항목을 추가한다.
`require_mount=true`인 경로가 마운트되지 않았거나 조회가 실패하면 UNKNOWN이며 정상으로 처리하지 않는다.

다음은 경로 예시이며 기존 서버 설치를 바꾸는 명령은 아니다.

```sh
# 전용 상태 디렉터리는 운영자가 먼저 0700으로 준비한다.
uv run python -m src.app.cli.disk_alerts \
  --config private-access/server-capacity-alerts.txt \
  --state private-access/server-capacity-state/state.json

# 명시적으로 활성화할 때만 아래 옵션을 추가한다.
# --send --loop
```

옵션 없는 기본 실행은 점검만 하고 메일 발송 상태를 소비하지 않는다. 실제 운영 설치는
별도로 설정한 서비스에서 `--send --loop`로 실행한다. 파일은 매 주기 다시 읽으므로
수신자·경고 기준·점검 주기 변경이 반영된다. 잘못된 설정·공개 권한·손상된 상태 파일은
실패 처리하며 수신자를 추정하거나 기존 상태를 초기화하지 않는다.

발송 프로세스는 전용 상태 파일과 별도 잠금을 사용해 동시에 하나만 실행한다.
상태는0600으로 원자 교체하고 디렉터리는0700이어야 한다. 메일 주소는 상태에 저장하지
않고 수신자 해시만 저장한다. 동일 경고의 반복 통보는 기본1시간 간격이고 상태 변경은
별도 통보한다. 최초 정상 상태에서는 메일을 보내지 않으며 정상 복귀 통보는 한 번만 한다.
발송 전 PENDING 의도를 기록해 중간 종료 뒤의 중복 발송을 방지한다. UNKNOWN/PENDING은
동일 상태에서 자동 재발송하지 않는다. 상태 파일을 지워 재발송시키지 말고 별도로 조사한다.
명시적 거부는 알림 주기 뒤 재시도할 수 있다. 상태 쓰기가 실패하면 발송하지 않는다.

Gmail 발신 계정·send-only 인증은 기존 `GMAIL_*` 운영 환경 설정을 사용한다.
기존 인증 파일을 복사·변경하거나 업무 메일 워커를 시작하지 않는다.
프로세스 표준 출력은 디스크 상태와 기록된 전달 상태 수만 표시하고 주소·DSN·토큰은 출력하지 않는다.
ACCEPTED는 메일 제공자의 접수이며 실제 수신함 도착을 보장하지 않는다.
기록된 상태 수는 이전 주기의 결과를 포함할 수 있으며 이번 점검의 발송 건수가 아니다.

서버 자체가 꺼지거나 네트워크가 끊기면 같은 서버의 작업은 통보할 수 없다.
그 범위는 외부 감시가 필요하다. 이 도구는 DB 행 보관·공간 회수 설계를 대신하지 않는다.

## 적용 완료 기준

코드·설정 파일 준비, 서버 설치·주기 실행, 발신 설정 확인, 제공자 접수, 실제 메일 수신을
각각 검증한다. 실제 수신자 주소가 비어 있거나 enabled=false이면 감시 알림 가동 완료로
보고하지 않는다. 기존 데이터·보관 기간·다른 서비스·Git/SSH/VPN 설정은 변경하지 않는다.
